What it is

kudasai is a small Go binary that reads a .kudasai.json file from the current directory and runs the command you ask for. That is the whole tool.

The file lives in the repository, so the commands travel with the code. A new teammate runs kudasai test on day one without asking anyone which flags this project needs. When the build command changes, it changes in one place.

There is no runtime to install, no plugin system and no daemon. Commands run through sh -c in your working directory, with stdin, stdout and stderr wired straight to your terminal, and the exit code passed back to your shell.

Installation

Download the binary for your platform:

curl -fsSL https://raw.githubusercontent.com/vibaiher/kudasai/main/install.sh | sh

Or, with Go already on your machine:

go install github.com/vibaiher/kudasai@latest

Builds are published for Linux and macOS, on both amd64 and arm64.

Getting started

Scaffold a config in your project:

kudasai --init

kudasai looks for a marker file to work out what kind of project it is — go.mod, package.json, Gemfile, composer.json, pyproject.toml or requirements.txt — and proposes build, start, test and lint for it. It shows you the file first and asks before writing.

You can also write it by hand:

{
  "commands": {
    "build": {
      "run": "go build -o myapp main.go",
      "description": "Build the binary"
    },
    "test": {
      "run": "go test -v ./tests/...",
      "description": "Run unit tests"
    },
    "deploy": "git push origin main"
  }
}

Then ask for what you want:

kudasai build
kudasai test
kudasai deploy

Command format

A command can be written two ways.

As a string, when the name says enough:

{
  "commands": {
    "deploy": "git push origin main"
  }
}

As an object, when you want a description:

{
  "commands": {
    "deploy": {
      "run": "git push origin main",
      "description": "Deploy to production"
    }
  }
}

Both forms mix freely in the same file. Descriptions show up in --help and --json, which is where they earn their keep: they are how a teammate, or an agent, finds out what deploy actually does without reading the shell command.

Passing arguments

Anything you type after the command name is passed through. By default it lands at the end:

$ kudasai test -run TestFoo
→ go test -v ./tests/... -run TestFoo

Use placeholders when the end is the wrong place:

$1, $2, $N
a single positional argument
$@
every argument, in order
{
  "commands": {
    "test": "go test $@ ./tests/...",
    "greet": "echo hello $1, welcome to $2"
  }
}
$ kudasai test -v -run Foo
→ go test -v -run Foo ./tests/...

$ kudasai greet world earth
→ echo hello world, welcome to earth

Arguments are shell-quoted before they are substituted, so paths with spaces and strings with quotes survive the trip intact. A placeholder with no matching argument resolves to nothing.

Interactive commands

stdin is connected, so commands that expect a human still work. An editor opens, a prompt waits, a pager pages. 

{
  "commands": {
    "commit": "git add . && git commit",
    "console": "bundle exec rails console"
  }
}

Built-in flags

Everything kudasai does itself is behind a -- flag. Every other name is yours, including help, init and check if you want them.

FlagWhat it does
--helpList the commands available here, with their descriptions
--versionPrint the installed version
--initScaffold a .kudasai.json, detecting the project type
--init --forceScaffold over an existing .kudasai.json
--checkValidate the config and count the commands in it
--jsonPrint the commands as structured JSON

AI agents

A coding agent dropped into an unfamiliar repository has to guess how to build and test it. --json removes the guessing: one command, and it has the list.

Add a line to your agent context file — AGENTS.md, CLAUDE.md, .cursorrules:

Run `kudasai --json` to discover available commands in this
repository. Use `kudasai <command>` to execute them.

That is all the setup. The output looks like this:

$ kudasai --json
{
  "commands": {
    "build": {
      "run": "go build -o kudasai main.go",
      "description": "Build the binary"
    },
    "test": {
      "run": "go test -v ./tests/...",
      "description": "Run unit tests"
    },
    "start": {
      "builtin": true
    }
  }
}

Descriptions are worth writing for this reason alone. They are the difference between an agent knowing that acceptance exists and knowing when to reach for it.
